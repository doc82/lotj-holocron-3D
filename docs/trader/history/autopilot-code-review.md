# AutoPilot review and Holocron implementation gaps

Reviewed 2026-09-05. Baseline: Xavious/AutoPilot commit `c8f0e6ff3d293c562cad452a3b62b5b7f3d8ac01`, package version 2.0.4. Upstream HEAD was checked against the local sibling checkout. This is a static review, not a live flight validation.

Scope: main Lua script, flight and cargo trigger definitions and handlers, aliases, ship/route/manifest/pad configuration, pause/resume and persistence, Geyser GUI, updater, README and package metadata. No automated test suite is present in the tracked tree. The local checkout has an uncommitted economy scanner/optimizer and cargo-state reset changes; those are not upstream capabilities.

## Conclusion

Implementation update: route cards now prepare the generic runner, with explicit start/resume/pause/stop controls and a packaged Mudlet navigation transport. The controlled live-test procedure is in `docs/trader/AUTOPILOT_TEST.md`. This supersedes the earlier statement that the runner is not connected. Recovery currently requires standing outside the ship at the expected stop; arbitrary aboard recovery remains outstanding.

Update after user clarification: stations use the same landing workflow as planets; no separate docking protocol is needed. Bare `showplanet` identifies the current planet when on one. `credits` returns `You have 1097793 credits.` Already-full refueling returns `That ship is already fully fueled!` and is successful with zero cost. These observations supersede the corresponding information requests below. GMCP is a source for aboard/outside reconciliation, but its exact transitions still need to be handled by the adapter rather than inferred from an old cached ship object.

Implemented in Holocron after that clarification: credit balance parsing/capture and timestamped telemetry; successful already-full refueling; timestamped current-planet observations only for bare `showplanet`/`showp`, never named lookups. Regression coverage includes those distinctions. Full live autopilot wiring and GMCP access-state reconciliation remain outstanding.

The source supplies the ordinary planet-flight and cargo command sequences. Another complete flight transcript is unnecessary before implementation. Holocron still needs a transport adapter and confirmation/recovery handling; station operations and independent startup/resume observations are the main remaining protocol gaps.

| Accounting    | Actual profit is sales minus purchases minus paid fuel. Profit/hour is profit divided by elapsed seconds, multiplied by 3600. Paused time remains in elapsed time. This measures realized performance, rather than predicting an unflown route.      |

## Findings to address when adapting the behavior

1. **High: stop does not cancel scheduled commands.** The landing handler schedules a command after two seconds; hyperspace failure schedules another jump after twenty seconds. Timer IDs are not retained, and disabling trigger groups does not cancel already scheduled callbacks. Holocron must cancel timers and invalidate callbacks on stop, pause and replacement missions. See [landing timer](https://github.com/Xavious/AutoPilot/blob/c8f0e6ff3d293c562cad452a3b62b5b7f3d8ac01/src/scripts/autopilot.script.lua#L1158) and [retry handler](https://github.com/Xavious/AutoPilot/blob/c8f0e6ff3d293c562cad452a3b62b5b7f3d8ac01/src/scripts/autopilot.script.lua#L1226).
2. **High: progression is not correlated with a pending action.** Broad triggers and `!` retries can react to unrelated output or repeat a different command. Cargo purchase/sale handlers do not validate the observed resource and amount against the expected transaction. Boarding and cockpit movement are sent as a sequence without confirming each result. Holocron needs exclusive execution ownership, phase-specific matching, bounded retries, and reconciliation after ambiguity. See [handlers](https://github.com/Xavious/AutoPilot/blob/c8f0e6ff3d293c562cad452a3b62b5b7f3d8ac01/src/scripts/autopilot.script.lua#L1077).
3. **High: resume restores intent without observing reality.** Saved delivery indices and totals are restored; the user's sell-first choice determines whether cargo is sold or bought. Location, ship access, current cargo and available credits are not checked. Pause guards are also not present at every flight transition. Holocron must reconcile before resuming after interruption. See [pause/resume](https://github.com/Xavious/AutoPilot/blob/c8f0e6ff3d293c562cad452a3b62b5b7f3d8ac01/src/scripts/autopilot.script.lua#L952).
4. **Medium: restricted-pad fallback can address missing state.** A preferred-pad rejection can reach the fallback without an initialized pad index/list. Exhausting listed pads is also unchecked. Block with a useful reason or collect fresh choices before retrying. See [pad handlers](https://github.com/Xavious/AutoPilot/blob/c8f0e6ff3d293c562cad452a3b62b5b7f3d8ac01/src/scripts/autopilot.script.lua#L1136).
5. **Medium: contraband selection can use the wrong delivery.** After a sale, the next resource is bought using the previous delivery's contraband setting. Also, `delivery.contraband or globalFlag` cannot express an explicit false override. The contraband-sale regex has a suspicious resource character class and should be validated with a fixture before reuse. See [selection helper](https://github.com/Xavious/AutoPilot/blob/c8f0e6ff3d293c562cad452a3b62b5b7f3d8ac01/src/scripts/autopilot.script.lua#L1067), [next purchase](https://github.com/Xavious/AutoPilot/blob/c8f0e6ff3d293c562cad452a3b62b5b7f3d8ac01/src/scripts/autopilot.script.lua#L1264) and cargo definitions above.
6. **Medium: mutable configuration can change a run's meaning.** Deliveries reference routes by array index; deleting a route shifts subsequent indices. GUI manifest edits mutate saved state before final Save, and matching delivery counts can cause an unrelated active manifest to be updated. Use stable IDs, draft edits and a frozen mission snapshot. See [main source configuration and GUI](https://github.com/Xavious/AutoPilot/blob/c8f0e6ff3d293c562cad452a3b62b5b7f3d8ac01/src/scripts/autopilot.script.lua).
7. **Medium: paid refuel output is accounting, not a completion gate.** The script continues without waiting for it. It does not establish already-full, unavailable-fuel or insufficient-credit responses. Holocron must distinguish success, no-op and failure rather than time out when no payment occurs.
8. **Medium: updater has no rollback.** It uninstalls before checking whether installation succeeds, and lacks download-error handling. This mechanism is unnecessary for the navigation adapter. See [updater](https://github.com/Xavious/AutoPilot/blob/c8f0e6ff3d293c562cad452a3b62b5b7f3d8ac01/src/scripts/autopilot.script.lua#L2984).

Additional compatibility work: quote multiword names consistently; preserve Holocron's current bidirectional gateway and distance constraints; refresh hyperlane availability at appropriate checkpoints. Upstream executes user-defined waypoints rather than validating or replanning them. Do not import the local economy scanner's older galaxy assumptions.

## Holocron implementation sequence

1. Add the known AutoPilot messages as fixtures and implement a Mudlet navigation adapter with an explicit state machine. Keep navigation separate from cargo actions so a non-cargo planner can use the same mission runner.
2. Wire the existing generic runner to typed commands and confirmed telemetry, with action correlation, durable checkpoints, timeout handling and cancellation. Prevent two autopilot packages from driving the ship simultaneously.
3. Connect in-app arm/start/pause/resume/stop and show the pending action or blocked reason. Use named orbit plus the issued landing and touchdown to confirm an uninterrupted planet arrival; require fresh reconciliation after interruption.
4. Attach cargo actions, cargo reconciliation, affordability checks and actual transaction accounting. Preserve estimated profit/hour and show realized profit/hour separately.
5. Add the station adapter once its protocol is available. Validate a complete loop including a transit stop, interruption and recovery in Mudlet.

The existing generic runner is groundwork, not a connected live autopilot. This review changes the fixture requirements: normal planet-flight implementation can proceed using this source, without asking the user to reproduce the full journey.
